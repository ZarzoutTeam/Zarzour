# خطة وتوصيف تعديلات الكلاينت - لوحة الإدارة والباك إند

> **حالة التنفيذ - 15 آب 2026:** تم تنفيذ نطاق الباك إند والداشبورد الموصوف في هذه الوثيقة. بقي تشغيل migrations وShield seeder وبناء أصول Vite على بيئة تحتوي PHP، ثم ربط حقول الـAPI الجديدة بواجهة المتجر. تعديلات CSS الخاصة بواجهة المتجر نفسها ليست ضمن هذا المستودع.

## 1. هدف الوثيقة

تحوّل هذه الوثيقة ملاحظات الكلاينت الواردة في ملف **«تعديلات على موقع فتنس»** إلى نطاق عمل واضح يخص:

- لوحة الإدارة المبنية بـ Filament.
- منطق Laravel والبيانات والتخزين والكاش.
- عقود الـ API التي تحتاجها واجهة المتجر.
- اختبارات القبول والتشغيل المرتبطة بهذه التعديلات.

لا تشمل الوثيقة تنفيذ التصميم العام لواجهة المتجر. نقاط الفرونت إند مذكورة فقط لتحديد الحدود والاعتماديات ومنع احتسابها خطأ ضمن عمل الباك إند.

## 2. الملخص التنفيذي

بعد مطابقة طلبات الكلاينت مع الكود الحالي، تنقسم الأعمال إلى أربع مجموعات:

1. **إصلاحات على وظائف موجودة:** ظهور البانر، ظهور صور المنتجات، وثبات ظهور الفئات مباشرة بعد الحفظ.
2. **ميزات جديدة:** عرض «هدية فقط»، وإدارة صورة/فيديو الـ Hero من لوحة الإدارة، وإضافة سعر بالليرة السورية وسعر بالدولار.
3. **تحسينات تجربة لوحة الإدارة:** صوت الإشعارات، إبراز زر الإشعارات، والعودة إلى قائمة الوحدة بعد الحفظ.
4. **طلبات خارج نطاق الباك إند المباشر:** خلفيات عناوين صفحات المتجر، تكبير حقل نطاق السعر، وعرض طرق الدفع بصريًا في صفحة المتجر.

هناك فجوة تقنية واضحة في الكود الحالي قد تفسر جزءًا من مشكلات الصور: تغييرات ملفات الميديا نفسها لا تبطل دائمًا كاش الصفحة الرئيسية. يوجد Observer لوسائط المنتجات، لكنه لا يمسح `home.public.snapshot` عند تغيير صورة المنتج، ولا يعالج وسائط البانرات. لذلك قد يبقى الـ API يعيد لقطة قديمة حتى لو تم رفع الملف بنجاح.

## 4. الوضع الحالي المؤكد من الكود

### 4.1 البانرات

الموجود حاليًا:

- شاشة Filament لإنشاء وتعديل وحذف وترتيب البانرات.
- صورة إلزامية لكل بانر وتحويلات WebP بأحجام `thumbnail` و`medium` و`hero`.
- ربط البانر بمنتج.
- تفعيل، أولوية، وقت بداية، ووقت نهاية.
- إرجاع البانرات ضمن `GET /api/v1/home` و`GET /api/v1/banners`.
- كاش لمدة خمس دقائق للمسارين.

الفجوة المهمة: `BannerObserver` يمسح الكاش عند حفظ سجل البانر، لكن إضافة/استبدال ملف الصورة تتم عبر سجل Media منفصل بعد حفظ السجل. لا يوجد حاليًا تعامل مع Media الخاصة بالبانر لمسح الكاش بعد اكتمال تغيير الملف.

### 4.2 صور المنتجات

الموجود حاليًا:

- رفع عدة صور وإعادة ترتيبها، بالإضافة إلى فيديو واحد.
- أول صورة بحسب `order_column` هي الصورة الأساسية.
- إرجاع الصورة المصغرة في قوائم المنتجات، وإرجاع كل الوسائط في تفاصيل المنتج.
- تحويلات الصور تنفذ بشكل غير مؤجل إلى WebP.

الفجوة المهمة: `ProductMediaObserver` يمسح كاش البانرات إذا كان المنتج مرتبطًا ببانر، لكنه لا يمسح كاش `home.public.snapshot`. لذلك قد تبقى أقسام أحدث المنتجات أو المنتجات المميزة بصورة قديمة أو فارغة.

### 4.3 الفئات

الموجود حاليًا:

- فئات رئيسية وفئات فرعية.
- لا يعرض الـ API إلا الفئات الرئيسية النشطة في المستوى الأعلى؛ الفئات الفرعية تظهر داخل `children`.
- `CategoryObserver` يمسح كاش شجرة الفئات وكاش الصفحة الرئيسية عند الحفظ والحذف.
- كاش `/categories` مدته ست ساعات، وكاش `/home` مدته خمس دقائق.

لا توجد فجوة ثابتة ظاهرة من القراءة وحدها، لذلك يجب إعادة إنتاج المشكلة. الاحتمالات الأقوى هي: إنشاء الفئة كفرعية، عدم تفعيلها، كاش واجهة المتجر، اختلاف مخزن الكاش بين العمليات، أو عدم وصول نسخة النشر إلى الـ Observer الحالي.

### 4.4 العروض

الموجود حاليًا:

- `discount_only`: خصم فقط.
- `discount_with_gift`: خصم مع هدية.
- الهدية دائمًا قطعة واحدة لكل سطر سلة، وليس لكل وحدة مشتراة.
- إذا نفد مخزون الهدية يتحول العرض الحالي بصمت إلى خصم فقط.
- يمنع تداخل عرضين نشطين للمنتج نفسه.

لا يوجد نوع `gift_only`، وحقلا نوع الخصم وقيمته إلزاميان في قاعدة البيانات والنموذج.

### 4.5 الأسعار والعملات

كل المنتج، السلة، الطلب، الشحن، الخصومات، الكوبونات، ولقطات سعر الطلب تعتمد حاليًا أرقامًا بلا حقل عملة. بيانات الـ Seeder تشير عمليًا إلى أن `price` الحالي بالليرة السورية، لكن ذلك غير مصرح به في المخطط أو استجابة الـ API.

### 4.6 الإشعارات

الموجود حاليًا:

- إشعار طلب جديد.
- إشعار محاولة شراء كمية غير متوفرة.
- تخزين الإشعارات في قاعدة البيانات وإظهارها داخل Filament.
- الإرسال يعمل عبر Queue، لذلك يحتاج Queue Worker في بيئة التشغيل.

غير الموجود: صوت عند وصول إشعار جديد، وتمييز بصري خاص لزر الجرس عندما توجد إشعارات غير مقروءة.

### 4.7 التنقل بعد الحفظ

صفحات الإنشاء والتعديل تستخدم سلوك Filament الافتراضي. عند إنشاء سجل له صفحة تعديل، يعيد Filament المستخدم إلى صفحة تعديل السجل الجديد، وليس إلى القائمة. لذلك طلب الكلاينت غير متحقق حاليًا.

### 4.8 طرق الدفع

الباك إند يقبل القيم التالية عند إنشاء الطلب:

- `cod`: الدفع عند الاستلام.
- `sham_cash`: شام كاش.
- `visa_ui`: فيزا كخيار واجهة.

هذه قيم ثابتة في التحقق وقاعدة البيانات، ولا يوجد Endpoint عام يعيد قائمة طرق الدفع المتاحة، ولا يوجد تكامل دفع إلكتروني فعلي أو تأكيد عملية دفع. الاسم `visa_ui` يدل على خيار عرض، وليس بوابة دفع مكتملة.

## 5. التوصيف التقني التفصيلي

### 5.1 ADM-01 وADM-04: ظهور البانرات وصور المنتجات

#### الهدف

أي صورة تُرفع أو تُستبدل من لوحة الإدارة يجب أن تظهر في استجابة الـ API العامة مباشرة بعد نجاح الحفظ، من دون انتظار انتهاء TTL للكاش، ويجب أن تكون روابط الملفات صالحة من خارج السيرفر.

#### التصميم المقترح

1. إنشاء مسؤول واحد عن إبطال كاش الكتالوغ بدل توزيع أسماء مفاتيح الكاش كنصوص في عدة Observers، مثل `CatalogCacheInvalidator`.
2. توسيع Observer الميديا ليعالج:
   - `Product` ضمن collection اسمها `images`: مسح كاش الصفحة الرئيسية.
   - صورة منتج مرتبط ببانر: مسح كاش البانرات والصفحة الرئيسية.
   - `Banner` ضمن collection اسمها `image`: مسح كاش البانرات والصفحة الرئيسية.
   - وسائط الـ Hero الجديدة لاحقًا: مسح كاش الصفحة الرئيسية.
3. تنفيذ الإبطال على أحداث `saved` و`deleted` الخاصة بـ Media، لأن استبدال الملف عادة يعني حذف Media قديمة وإنشاء Media جديدة.
4. إبقاء إبطال الكاش في Observers النماذج عند تغيير العنوان أو التفعيل أو الترتيب أو الفترة الزمنية.
5. إضافة فحص تشغيلي لبيئة النشر:
   - وجود `public/storage` أو إعداد S3 صحيح.
   - تطابق `APP_URL` مع الدومين والبروتوكول HTTPS الفعلي.
   - أن يكون `MEDIA_DISK` عامًا أو يولد روابط عامة صحيحة.
   - توفر GD/Imagick ودعم WebP.
   - نجاح إنشاء ملفات conversions وعدم إعادة رابط إلى ملف غير موجود.
6. إضافة حالة ظهور واضحة في جدول البانرات: «ظاهر الآن»، «غير مفعّل»، «لم يبدأ»، «منتهي»، و«الصورة مفقودة».
7. يفضّل إضافة إجراء «معاينة الرابط» في لوحة الإدارة لفتح ملف الـ Hero الناتج مباشرة.

#### التحقق والاختبارات

- إنشاء بانر نشط بصورة ثم طلب `/api/v1/banners` و`/api/v1/home` والتأكد من وجود URL غير فارغ.
- استبدال صورة بانر بعد تكوين الكاش والتأكد أن الطلب التالي يعيد URL الجديدة.
- إنشاء منتج من دون صورة، تكوين كاش الصفحة الرئيسية، ثم رفع صورة والتأكد أن الطلب التالي يعيد الصورة.
- إعادة ترتيب صور المنتج والتأكد أن الصورة الأولى الجديدة تصبح `thumbnail` في القوائم.
- اختبار حالات البانر: غير مفعّل، مستقبلي، منتهٍ، ونشط.
- اختبار أن رابط الملف يرجع HTTP 200 من بيئة staging، وليس فقط أن النص موجود في JSON.

#### معايير القبول

- لا يحتاج المستخدم إلى مسح الكاش يدويًا بعد رفع صورة.
- صورة البانر وصورة المنتج المحدثة تظهران في أول استجابة API بعد اكتمال الحفظ.
- لا تحتوي الاستجابة على رابط Conversion غير موجود.
- توضح لوحة الإدارة سبب عدم أهلية أي بانر للظهور.

### 5.2 ADM-02: نوع عرض «هدية فقط»

#### الهدف

إنشاء عرض يمنح منتج هدية عند شراء المنتج الأساسي من دون تطبيق أي خصم مالي.

#### تغييرات البيانات

- إضافة قيمة `gift_only` إلى نوع العرض.
- جعل `discount_type` و`discount_value` قابلين لأن يكونا `null` لعرض الهدية فقط.
- الحفاظ على البيانات الحالية بلا تغيير:
  - `discount_only` يحتاج حقول الخصم.
  - `discount_with_gift` يحتاج حقول الخصم وهدية.
  - `gift_only` يحتاج هدية ولا يحتاج حقول الخصم.

#### تغييرات لوحة الإدارة

- إضافة خيار «هدية فقط» في حقل نوع العرض.
- إخفاء حقلي نوع الخصم وقيمة الخصم عندما يكون النوع `gift_only`، وعدم إرسالهما كقيم قديمة مخفية.
- إظهار حقل منتج الهدية وإلزامه لكل من `gift_only` و`discount_with_gift`.
- عرض أسماء الأنواع بالعربية في الجدول بدل القيم البرمجية.
- عرض قيمة الخصم كشرطة `—` في عرض الهدية فقط.
- حفظ العرض وعلاقة الهدية داخل Transaction واحدة لمنع إنشاء عرض ناقص إذا فشل حفظ الهدية.

#### تغييرات منطق التسعير

- `gift_only`: قيمة الخصم تساوي صفرًا دائمًا، مع محاولة إضافة الهدية.
- `discount_with_gift`: يبقى السلوك الحالي، خصم ثم هدية.
- `discount_only`: يبقى السلوك الحالي بلا هدية.
- قاعدة عدم تداخل العروض تبقى مطبقة على الأنواع الثلاثة.

#### عقد الـ API

يجب أن تعرض تفاصيل المنتج نوع العرض وبيانات الهدية اللازمة للواجهة، مثل:

```json
{
  "type": "gift_only",
  "discount": null,
  "gift": {
    "product_id": 42,
    "name": "قفازات رياضية",
    "available": true
  }
}
```

ويجب أن تبقى نتيجة حساب السلة هي المصدر النهائي للحكم على توفر الهدية، لأن المخزون قد يتغير بعد فتح صفحة المنتج.

#### قرارات عمل مطلوبة

التوصية الافتراضية إلى أن يطلب الكلاينت غير ذلك:

- الهدية قطعة واحدة لكل سطر سلة، كما هو السلوك الحالي.
- إذا نفدت هدية عرض `gift_only` يستمر إنشاء الطلب بلا هدية وبلا خصم، مع إرجاع حالة واضحة في حساب السلة أن العرض غير متاح، بدل إظهار أنه طُبق.
- لا يتم حجز الهدية عند معاينة السلة؛ الحجز يتم عند إنشاء الطلب.

يجب تأكيد إن كانت الهدية «واحدة لكل طلب»، «واحدة لكل سطر»، أم «واحدة لكل قطعة مشتراة»، لأن ذلك يغير المخزون والتسعير.

#### الاختبارات

- هدية فقط مع مخزون متاح: الخصم صفر ويضاف سطر هدية مجاني.
- هدية فقط مع مخزون نافد: لا خصم ولا سطر هدية، والطلب لا يفشل وفق السياسة المقترحة.
- منع عرض gift-only متداخل مع عرض نشط آخر للمنتج نفسه.
- الإنشاء والتعديل من Filament يحفظان علاقة الهدية الصحيحة ويحذفان العلاقة عند التحويل إلى `discount_only`.
- استجابة تفاصيل المنتج وحساب السلة والطلب متطابقة في نوع العرض.

### 5.3 ADM-03: إدارة صورة أو فيديو الواجهة الرئيسية

#### تفسير المتطلب

يجب اعتبار وسائط الـ Hero الرئيسية وحدة مستقلة عن البانرات، لأن الكلاينت ذكر البانر و«الصورة بالواجهة الرئيسية» كنقطتين منفصلتين. لا ينبغي خلط الحقلين ما لم يؤكد الكلاينت أن المقصود هو تحويل البانر نفسه إلى صورة/فيديو.

#### التصميم المقترح

إنشاء سجل Singleton مثل `HomepageMedia` يحتوي:

- `media_type`: `image` أو `video`.
- `is_active`.
- `updated_by` للتدقيق، إن أمكن.
- timestamps.
- Media collection مفردة للصورة وMedia collection مفردة للفيديو.
- صورة Poster اختيارية للفيديو، موصى بها لضمان عرض أول إطار قبل تشغيل الفيديو.

#### لوحة الإدارة

إنشاء صفحة «إعدادات الواجهة الرئيسية» تحتوي:

- اختيار النوع: صورة أو فيديو.
- رفع صورة عند اختيار image؛ الأنواع المقبولة JPEG/PNG/WebP والحجم حسب إعدادات الكتالوغ.
- رفع MP4 عند اختيار video، بحجم افتراضي أقصى 50MB.
- Poster اختياري للفيديو.
- معاينة الوسائط الحالية.
- تفعيل/تعطيل.
- منع وجود أكثر من إعداد فعّال واحد.
- صلاحية Shield مستقلة لإدارة إعدادات الصفحة الرئيسية.

عند تغيير النوع يجب حذف/فصل ملف النوع السابق بعد نجاح الحفظ، لا قبله، لتجنب فقدان الوسائط إذا فشل الرفع الجديد.

#### عقد الـ API

إضافة حقل مستقل إلى `/api/v1/home`:

```json
{
  "hero_media": {
    "type": "video",
    "url": "https://example.com/storage/.../hero.mp4",
    "poster_url": "https://example.com/storage/.../poster.webp",
    "updated_at": "2026-08-15T12:00:00Z"
  }
}
```

إذا لم توجد وسائط فعالة تكون القيمة `null`. يجب عدم تغيير بنية `banners` الحالية.

#### الكاش والاختبارات

- مسح `home.public.snapshot` عند تغيير سجل الإعداد أو أي Media تابعة له.
- اختبار التبديل من صورة إلى فيديو ومن فيديو إلى صورة.
- اختبار رفض MIME أو حجم غير مسموح.
- اختبار أن `/home` يعيد ملفًا واحدًا فقط وبالنوع الصحيح.
- اختبار حذف/تعطيل الوسائط وإرجاع `null` مباشرة بلا انتظار الكاش.

### 5.4 ADM-05: ثبات ظهور الفئات

#### الهدف

الفئة النشطة يجب أن تظهر في أول طلب API بعد الحفظ ضمن المكان الصحيح من الشجرة.

#### خطة المعالجة

1. إعادة إنتاج السيناريو على staging مع تسجيل:
   - هل الفئة رئيسية أم فرعية؟
   - قيمة `is_active`.
   - استجابة `/api/v1/categories` واستجابة `/api/v1/home` بعد الحفظ مباشرة.
   - مخزن الكاش المستخدم في لوحة الإدارة والـ API.
2. توحيد إبطال كاش الفئات والصفحة الرئيسية في خدمة واحدة.
3. جعل إبطال الكاش يحدث بعد نجاح Commit إذا كانت عملية الحفظ داخل Transaction، لتجنب إعادة بناء الكاش من بيانات لم تعتمد بعد.
4. إضافة عمود «مكان الظهور» في جدول الفئات:
   - رئيسية: تظهر في المستوى الأول.
   - فرعية: تظهر داخل اسم الفئة الأب.
   - غير مفعّلة: لا تظهر.
5. إضافة مساعدة واضحة في النموذج بأن اختيار فئة أب يجعل السجل فرعيًا ولن يظهر كبطاقة رئيسية مستقلة.
6. التحقق من أن عملية النشر لا تستخدم نسخًا مختلفة من cache prefix أو config cache بين لوحة الإدارة والـ API.

#### الاختبارات

- إنشاء فئة رئيسية نشطة بعد تكوين الكاش ثم التأكد من ظهورها فورًا في endpointين.
- إنشاء فئة فرعية نشطة والتأكد من ظهورها داخل `children` فقط.
- تعطيل فئة والتأكد من اختفائها مباشرة.
- تغيير parent والترتيب والتأكد من انتقالها وترتيبها بلا تأخير.
- حذف فئة غير مرتبطة والتأكد من اختفائها مباشرة.

#### معايير القبول

- لا يتجاوز ظهور التغيير زمن الطلب التالي للـ API.
- تتطابق شجرة `/home` مع `/categories`.
- تشرح لوحة الإدارة للمستخدم مكان ظهور الفئة قبل الحفظ.

### 5.5 ADM-06: السعر بالليرة السورية والدولار

#### القرار الموصى به للنطاق الحالي

إضافة سعرين مستقلين يحررهما مسؤول المتجر يدويًا:

- `price_syp`: السعر بالليرة السورية.
- `price_usd`: السعر بالدولار الأمريكي.

عدم الاعتماد على سعر صرف تلقائي في هذه المرحلة، لأن المتطلب يقول «إضافة السعرين» ولا يحدد مصدر سعر صرف أو توقيت تحديثه.

#### الهجرة والتوافق

1. اعتبار `price` الحالي سعر SYP عند الترحيل، بعد تأكيد ذلك من صاحب المشروع.
2. إضافة `price_syp` و`price_usd` مع دقة مناسبة؛ يوصى بـ `DECIMAL(14,2)` لـ SYP و`DECIMAL(10,2)` لـ USD.
3. تعبئة `price_syp` من `price` الحالي.
4. إبقاء `price` في استجابة API لفترة توافق واحدة على أنه SYP، مع إضافة بنية جديدة:

```json
{
  "price": 85000,
  "prices": {
    "SYP": 85000,
    "USD": 6.5
  }
}
```

5. بعد تحديث الفرونت إند يمكن إهمال `price` القديم في نسخة API لاحقة، لا حذفه فجأة من v1.

#### لوحة الإدارة

- حقل «السعر بالليرة السورية» وحقل «السعر بالدولار» مع لاحقة العملة.
- كلاهما غير سالب؛ وتحدد إلزامية USD بعد تأكيد الكلاينت إن كان مسموحًا أن يكون المنتج بلا سعر دولار.
- إظهار عمودين في جدول المنتجات.
- تحديث البانرات واستجابات المنتج لتعيد السعرين.
- تحديث قواعد مسح الكاش لتشمل الحقلين.

#### حد النطاق المهم

إظهار سعرين لا يعني أن النظام صار ينشئ طلبات بعملتين. الطلبات الحالية لا تحفظ `currency`، وكل الخصومات والكوبونات ورسوم الشحن ولقطات الأسعار تعتمد عملة واحدة.

التوصية للمرحلة الأولى: يبقى الحساب والدفع والطلبات بالليرة السورية، ويكون سعر USD للعرض فقط.

إذا أراد الكلاينت Checkout بالدولار أيضًا، يلزم Scope منفصل يشمل:

- اختيار العملة في حساب السلة وإنشاء الطلب.
- `currency` على الطلب ولقطات الأسعار.
- قيم كوبونات وخصومات ثابتة لكل عملة أو قاعدة تحويل واضحة.
- رسوم شحن بالدولار.
- تقارير ومؤشرات مبيعات مجمعة حسب العملة، من دون جمع SYP وUSD في رقم واحد.
- ربط طريقة الدفع بالعملات التي تدعمها.

#### الاختبارات

- ترحيل منتج قديم من دون خسارة السعر الحالي.
- إنشاء وتعديل السعرين من لوحة الإدارة.
- إرجاع السعرين في قائمة المنتجات، التفاصيل، البانرات، والصفحة الرئيسية.
- بقاء حساب الطلب بالليرة في النطاق المرحلي وعدم استخدام سعر USD بالخطأ.
- عمل فرز/فلترة السعر وفق العملة المحددة أو وفق SYP افتراضيًا.

### 5.6 ADM-07: صوت الإشعارات وإبراز زرها

#### التصميم المقترح

- إبقاء قاعدة البيانات والـ Queue كما هما؛ التعديل يخص سلوك لوحة الإدارة عند وصول إشعار جديد.
- إضافة CSS يستهدف زر `.fi-topbar-database-notifications-btn` عندما يحمل Badge غير مقروء، بلون تحذير واضح وتباين مناسب.
- إضافة ملف صوت قصير مخصص للوحة الإدارة.
- تشغيل الصوت فقط عندما يزداد عدد الإشعارات غير المقروءة أثناء الجلسة، وليس عند كل Refresh أو عند فتح صفحة فيها إشعارات قديمة.
- تهيئة الصوت بعد أول تفاعل للمستخدم مع الصفحة بسبب قيود Autoplay في المتصفحات.
- إضافة كتم/تفعيل الصوت محفوظًا في `localStorage`، موصى به لتجنب إزعاج المستخدم.
- ضبط Polling للإشعارات بزمن واضح، أو استخدام بث لحظي لاحقًا إذا كان المشروع سيضيف WebSockets.

#### معايير القبول

- وصول إشعار جديد يزيد العداد ويغير شكل الزر ويشغل الصوت مرة واحدة.
- تحديث الصفحة لا يعيد تشغيل صوت الإشعارات القديمة.
- عند قراءة كل الإشعارات يعود الزر إلى حالته العادية.
- عدم سماح المتصفح بالصوت لا يكسر لوحة الإدارة؛ يبقى التنبيه البصري يعمل.
- Queue Worker عامل، وإلا لن يصل الإشعار أصلًا في الوقت المتوقع.

### 5.7 ADM-08: الرجوع إلى القائمة بعد الحفظ

#### التنفيذ المقترح

ضبط لوحة Filament على:

- `resourceCreatePageRedirect('index')` بعد إنشاء سجل.
- `resourceEditPageRedirect('index')` بعد تعديل سجل.

يفضل تطبيق ذلك مركزيًا في `AdminPanelProvider` ليشمل المنتجات والفئات والعروض والكوبونات والخصومات والبانرات والمحافظات، مع استثناء أي Resource مستقبلي يحتاج البقاء على صفحة التعديل.

#### معايير القبول

- إنشاء كوبون ناجح يعيد المستخدم إلى قائمة الكوبونات.
- تظهر رسالة نجاح، وتكون الإضافة الجديدة موجودة في القائمة وفق ترتيبها الافتراضي.
- تعديل سجل ناجح يعيد المستخدم إلى قائمة الوحدة نفسها.
- فشل التحقق يبقي المستخدم في النموذج ولا يغيّر الصفحة.
- إجراء «إنشاء وإضافة آخر» - إذا أبقيناه - يستمر بإظهار نموذج جديد بدل الرجوع إلى القائمة.

### 5.8 WEB-02: طرق الدفع - الجزء الخاص بالباك إند

#### الحالة الحالية

طرق الدفع موجودة كقيم ثابتة في الطلب فقط. لا توجد إدارة من لوحة التحكم ولا عقد عام ليعرف الفرونت إند ما الذي يجب عرضه.

#### الحد الأدنى المقترح

إضافة إعداد Checkout يعيده endpoint عام، مثل:

```json
{
  "payment_methods": [
    {"key": "cod", "label": "الدفع عند الاستلام", "enabled": true},
    {"key": "sham_cash", "label": "شام كاش", "enabled": true},
    {"key": "visa_ui", "label": "فيزا", "enabled": true}
  ]
}
```

ويجب أن يستخدم `StoreOrderRequest` المصدر نفسه للتحقق، كي لا يعرض الموقع خيارًا يرفضه الباك إند أو يقبل الباك إند خيارًا مخفيًا.

إذا كان المطلوب تمكين/تعطيل الطرق من لوحة الإدارة، تضاف صفحة إعدادات صغيرة مع تعليمات الدفع لكل طريقة. أما إذا كان المطلوب مجرد إظهار الخيارات الحالية، فهذا العمل يحتاج تعديل Frontend إضافة إلى عقد الـ API.

#### تنبيه نطاق

لا ينبغي وصف Visa أو Sham Cash كدفع إلكتروني متكامل قبل وجود بوابة دفع، callback/webhook، حالات دفع، مرجع معاملة، والتحقق من نجاح المبلغ. العرض البصري وحده ليس معالجة دفع.

## 7. خطة التنفيذ المقترحة

### المرحلة 0: تثبيت المشاكل على Staging

- تحديد ما إذا كانت «صورة الواجهة الرئيسية» مستقلة فعلًا عن البانرات.

**مخرج المرحلة:** تقرير أسباب مؤكد، وليس مسح كاش يدويًا كحل دائم.

### المرحلة 1: الإصلاحات السريعة والأساسية

- إصلاح إبطال كاش وسائط المنتج والبانر.

- إضافة حالة ظهور/أهلية في جداول البانرات والفئات.

**شرط الإغلاق:** البانر والصور والفئات تظهر فورًا في أول API request بعد الحفظ.

### المرحلة 2: الميزات الجديدة المستقلة

- إضافة `gift_only` مع تحديث التسعير والعلاقات والـ API والاختبارات.

- إضافة صوت الإشعارات وحالة زر غير المقروء.

**شرط الإغلاق:** كل ميزة تعمل من لوحة الإدارة حتى استجابة الـ API/الإشعار مع اختبارات قبول.

### المرحلة 3: الأسعار والدفع بعد تثبيت القرارات

- ترحيل السعر الحالي إلى SYP وإضافة USD.
- تحديث كل موارد API ذات الصلة مع توافق v1.
- تحديد هل USD للعرض فقط أم للطلب أيضًا.
- كشف طرق الدفع المتاحة للواجهة وتحديد إن كانت قابلة للإدارة.

**شرط الإغلاق:** لا توجد قيمة مالية مبهمة العملة، ولا يتم خلط عملتين في الطلبات أو التقارير.

### المرحلة 4: اختبار تكاملي وتسليم

- تحديث دليل لوحة الإدارة وعقد API وقائمة متغيرات البيئة المطلوبة.

## 9. قرارات يجب تثبيتها مع الكلاينت

هذه الأسئلة لا تمنع بدء إصلاحات P0 وRedirect، لكنها تمنع اعتماد التصميم النهائي للميزات الجديدة:

1. هل «صورة الواجهة الرئيسية» عنصر Hero مستقل أم المقصود أن البانر نفسه يقبل صورة أو فيديو؟
2. هل سعر USD للعرض فقط أم يستطيع العميل إتمام الطلب والدفع بالدولار؟
3. هل السعران يُدخلان يدويًا أم يحسب USD/SYP من سعر صرف؟ وإذا كان تلقائيًا فما المصدر ومتى يحدث التحديث؟
4. في عرض الهدية: هل الهدية واحدة لكل طلب، لكل سطر، أم لكل قطعة مشتراة؟
5. ماذا يحدث عندما تنفد هدية عرض «هدية فقط»: إخفاء العرض، منع الطلب، أم إكمال الطلب بلا هدية؟
6. هل طرق الدفع مجرد خيارات مرئية أم مطلوب تكامل دفع فعلي؟
7. هل العودة إلى القائمة مطلوبة بعد الإنشاء فقط أم بعد التعديل أيضًا؟ التوصية تطبيقها على الاثنين.
8. هل صوت الإشعار يعمل لكل مستخدمي الإدارة أم يكون لكل مستخدم خيار كتم مستقل؟ التوصية توفير الكتم.

7. تحقق يدوي على staging من الملفات العامة وQueue/Scheduler.
